# 设计取舍（DESIGN）

这份文档只解释「为什么这么做」，并且尽量写清楚**被否掉的那条路是什么**。
接口用法看 [README](../README.md)，接进宿主看 [PORTING](./PORTING.md)。

---

## 1. 目标与非目标

**目标**：给长期陪伴型 Agent 一套能自己跑很多个月的记忆底座，三条硬指标——

1. 召回**快**且**便宜**：一次召回是本地计算，不调模型、不连向量库。
2. 遗忘**讲道理**：忙的时候不忘，闲的时候慢慢淡，归档而不删除。
3. 说出口**不出事故**：编造、失约、复读、无脑顺着用户，在发送前被拦一次。

**非目标**（故意的）：

- 不做事实抽取。抽什么、怎么抽，取决于宿主的人设、场景和模型，底座统一抽只会四不像。
- 不做向量检索。陪伴场景的记忆量通常是几千条，中文二元组 + 权重臂已经够；引入 embedding 就把「零依赖、可离线」这条毁了。
- 不做提示词改写。「把回复改好」听起来很美，但改出来的句子不是她说的——那就成了另一个角色。

## 2. 双卡：衰减卡 + 原始账

| | 衰减卡 `jasmine.json` | 原始账 `ledger.jsonl` |
| --- | --- | --- |
| 写 | 覆盖写（原子 rename） | 只追加，每行一个操作 |
| 读 | 每次召回、每次出话核对 | 审计、重建、导出 |
| 坏了 | 从账本 `rebuildFromRaw()` 重建 | 丢了不影响召回，只丢审计 |
| 体积 | 有上限，`prune()` 控制 | 8MB 轮转成 `ledger.1.jsonl` |

为什么分两张：**状态和事实的生命周期不一样**。状态（权重、命中、是否被取代）天天变，
适合覆盖写；事实（她说过什么）永远不该被覆盖，适合追加。合成一张，要么每次写入都
重写整个文件（慢且危险），要么放弃「能重建」这个保险。

## 3. 衰减：按活跃天，不按自然天

```js
idle   = activeDays - lastActiveDay
grace  = GRACE_ACTIVE_DAYS[kind]        // address ∞ / promise 14 / event 7 ...
steps  = max(0, floor((idle - grace) / 7))
eff    = clamp(base - steps * 0.5, WEIGHT_FLOOR[kind], base)
```

三个刻意的选择：

1. **活跃天**：`touch()` 一天调一次，只有真正聊过天才推进。停机一周回来，记忆不该淡。
2. **只读不写**：`effectiveWeight()` 是**读取时的看法**，从不写回磁盘。写回会形成复利——
   每次读都扣一点，最后所有记忆一起归零。这是很多记忆系统翻车的根因。
3. **地板 + 宽限**：`promise`/`person` 这类掉到 3 分就不再掉（还抓得住），
   `event`/`meme` 掉到 1 分且闲置够 90 个活跃天，进归档而不是删除。

归档只针对 `event`/`meme`：这两类掉到地板本身已经说明「很久没提」，
而 `person`/`fact` 再旧也可能被重新提起，删掉就真没了。

## 4. 召回：RRF 两臂融合

关键词臂（中文二元组 + 英文词，命中越多分越高）和权重臂（`effectiveWeight` 越高越靠前）
各自排序，再用 RRF 融合：

```js
score = 0.6 / (60 + rankKeyword) + 0.4 / (60 + rankWeight)
```

- **K=60**：排名靠前的差距被压平，避免单个词命中就垄断结果。
- **0.6 / 0.4**：关键词略重。实测权重臂单独用时，老条目会因为分数高一直霸榜，
  关键词臂能把它拉回「这次到底在聊什么」。
- **融合后按字符预算裁**：`applyCharBudget(items, budget)`，预算由宿主给——
  同样的 200 条，聊天场景只放得下十几条，周报场景能放几十条。

`rank` 明细写进 `recall().trace`，调参时不用猜。

## 5. 出口核对：只核不改

六个维度，各带 0–1 置信：意图 / 情绪 / 关系 / 事实 / 风险 / 表达。
**它们互不投票**——不能让「语气好」抵消「编造事实」。

- **出处**：回复里引用的记忆编号必须在本轮召回集合里；对不上 = 编造。
- **承诺**：出现「答应/说好/承诺」就查未闭合清单；对不上 = 失约。
- **边界**：诊断、替代真实关系、绝对承诺，命中任一条就提醒。
- **复读**：4-gram 重叠 ≥ 0.60、句级字符二元组余弦 ≥ 0.85、前 20 字完全相同，
  任一命中记一次；**连续两次**才标记（一次可能是正常重复用词）。
- **迎合**：同意词 + 风险词或强度 ≥ 0.70 + 无 hedge，三条同时成立才 flag。

收敛成一个 `score`（事实 .3 / 风险 .3 / 表达 .2 / 关系 .1 / 意图 .1）和一行 `constraint`。

为什么不直接重写：重写会引入新的复读源（模型照着改写模板再说一遍），
而且会把「她说的」变成「核对器说的」。约束要短、要命令式，超过一行就会被当成剧情素材复述。

## 6. 压缩提醒：三档 + 最小回收

```
growth   可压量 ≥ 50K 且 距上次 ≥ 10K
pressure 窗口 ≥ 75%
urgent   窗口 ≥ 95%
minReclaim 能回收 < 5000 token 就不提醒
```

- 提醒**追加在本轮请求末尾**、**不写进历史**：写进历史等于改前缀，缓存全废。
- `minReclaim` 挡住「高频小折」：每轮都提醒一次、每次只省 2000 token，不但没用还烦。
- 三档而不是一档：75% 时给一次「现在压最划算」的机会，95% 时才强制。
  Molly 的实测数据：146 次提醒里 62 次发生在 >95%——上下文不是慢慢变满的，是突然变满的。

## 7. 每周一封信：模板，不是模型

信的内容 = 上周 event 卡 + 模板。为什么不让模型写：

1. 一周一封的调用成本 × 场景价值，不划算；
2. 模型写「总结」自带腔调，写出来像周报，不像人写给人；
3. 模板能保证每封信结构稳定，宿主可以放心把它当「长期记忆的索引」用。

`aggregateWeek()` 顺手把上周事件合成 level=2 的周记卡（原事件 level+1），
下次召回时「上周发生了这些」就是一条可用的上下文，而不是七条散事件。

## 8. 账本：按 purpose 分组

陪伴型 Agent 的花销跟聊天量不成正比：一次走神、一次压缩、一次核对都可能顶几十轮闲聊。
所以按 `chat / proactive / summary / verify / compaction / tool` 分组，
看「钱花在哪个动作上」，而不是只有一个总数。价格表由宿主给——价格会变，写死就是过时数据。

## 9. 群聊信号：四档，只否决最确定的那档

被叫 1.0 / 在说我 0.5 / 接我话 0.2 / 纯闲聊 0.01。宿主爱怎么用怎么用；
Molly 只在 `score === 0`（这条 @ 的是别人）时一票否决，其余档位只进决策日志。
理由：**改判定容易把她的脾气改没了**。先记日志，看几天真实分布再动阈值。

## 10. 已知限制

- 相似度用 Dice 二元组，对「同义不同词」不敏感（「住杭州」vs「在杭州生活」可能不合并）。
- 关键词臂对英语以外的拉丁语系不友好（只做小写和分词）。
- 核对层是规则 + 轻量统计，不做语义级事实核验；它只能抓「引用了不存在的编号」，抓不住「编号对但理解错」。
- `estimateTokens()` 是启发式估算（中文按字、英文按词），预算规划够用，计费请用真实 usage。
- 归档不会自动清理 `_archive.json`，长期运行需要宿主自己轮转。
