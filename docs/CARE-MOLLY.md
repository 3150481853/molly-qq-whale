# Molly 鱼崽养护说明（v1.1.5-A）

> 一句话：**她记得住的，靠你养；她记岔的，也靠你修。**
> 这份说明分两半：前半给饲养员（人）看，后半给 AI（DeepSeek / DSH 会话）看。
> 直接丢给 AI 的，可以只给「第二部分 + 附录」。

---

## 一、先给饲养员：为什么 1.1.5-A 之后要你动手

v1.1.5-A 把记忆「认人」这件事重做了一遍：新增 **`address`（称谓）** 这一类记忆。

旧库里的记忆是按当时那个笨办法写的——「他希望你叫他『宝宝』」「他希望你叫他『什』」这种半截话也照收。升级之后这些条目不会被自动改好，只会**继续躺在库里**，于是她还是会叫错人、还是会冒出听不懂的称呼。

所以升级后要做三件事：

1. **备份**（一定要先做）；
2. **重新分类**：把旧条目按新的七类重新归一遍，补上「谁希望被怎么叫」；
3. **清理**：把没意义、重复、过期的条目删掉，别让它把关键词分吃掉。

一次做不完没关系，分批做，做完在控制台抽查。

## 二、她到底记住什么（七个正式分类）

| kind | 是什么 | 例子 | 处理建议 |
|---|---|---|---|
| `fact` | 客观事实 | 「他在广州，养了一只叫团子的猫」 | 留；过期就改或删 |
| `preference` | 喜好 | 「他喜欢历史人物游戏」 | 留 |
| `person` | 对人的判断 | 「他人挺实在，就是话少」 | 留，但别太多 |
| `event` | 发生过的事 | 「他生日那天在加班」 | 旧的会过期，半年以上可清 |
| `promise` | 答应过的事 | 「他答应下周把书还我」 | 一定要留，别删 |
| `address` | **怎么称呼**（1.1.5-A 新增） | 「叫他『熊老板』」 | 每个活跃的人补一条 |
| `meme` | 梗/口头禅 | 「绷不住了，这波是典中典」 | 留少量，别堆 |

另外两类是系统自己写的，别手动加：`work`（干活的执行日志）、`sticker`（表情包学习）。

几个必须知道的规则：

- **`qq` 才是身份**，`who` 只是显示名。同一个人改了昵称，只要 `qq` 在，她照样认得出；
- `weight` 是「保留优先级」（1~5，默认 3），不是重要性评分。真正该给 5 的只有「这人是谁」那种；
- 单条 `text` 控制在 200 字内；写长了会被截断，但不会被自动清理，仍然占排序开销；
- 同一个人 + 相似度 ≥ 0.7 的新记忆会**覆盖旧的**（不是新增一条）。所以重复内容不会无限涨，但「新的把旧的盖掉」这件事要心里有数。

## 三、把「称谓」补对（这次升级的重点）

`address` 只吃这三种句式：

- 「叫他 X」「叫你 X」
- 「喊他 X」「喊你 X」
- 「称呼：X」「叫法「X」」

单字、疑问词、「一声/一句」这类量词，会被直接丢掉——这是为了防止再把「他希望你叫他『什』」这种半句话当名字。

补称谓的原则：

1. **一个人一条**，文本写「叫他『X』」；
2. 权重给 **5**（比普通记忆高，避免被裁剪压掉）；
3. 不确定的名字**别写**——她没记住时用群名片或「你」，比叫错强；
4. 群里打闹不许改成「哥们儿 / 兄弟 / 群友 / 老铁」——这是提示词里硬禁的。

## 四、清理无意义记忆（判据表）

| 情况 | 动作 | 理由 |
|---|---|---|
| 碎片转述（「他提到了 X 这个字」） | 删 | 没有信息量，还占关键词分 |
| 空断言（「他不在意」「他无所谓」） | 删 | 同上 |
| 重复条目（同人同义） | 删旧的，留新的 | 去重漏网的 |
| 半年以上的 `event` | 删或改写成 `fact` | 新鲜度会变负贡献 |
| 认错人的条目（`qq` 对不上） | 改 `qq` 或删 | 会让她叫错人 |
| 真名/敏感信息 | 改成昵称 | 隐私 |
| `promise`、`address` | **不要删** | 删了她会失约/乱叫人 |
| `insult` 类待核实 | 逐条看，别一键清空 | 这是设计上要你看见的 |

提醒：**记忆不会自动清理**。条数上限默认 2000，记满才按 `weight` + 时间淘汰；扩到 1 万之后一样。

---

## 五、三种养护频率

- **每周（10 分钟）**：控制台 → 记忆页，扫一眼 kind 分布和条数；看「待核实区」有没有堆 `fragment` / `vacuous`；
- **每月（半小时）**：让 DSH 跑一遍「重新分类 + 清理计划」，你逐条确认后执行；
- **每次升级后**：先备份，再跑一次重新分类；新版本可能会改 kind 的语义。

---

## 六、红线（别踩）

1. **不要直接改磁盘上的 `memory.json`**——现在是 AES-256-GCM 密文，插件又把整份文件放内存里，手改要么被覆盖，要么把库弄成 `broken` 只读；
2. **不要导入别人的记忆**——`qq` 是身份锚点，跨人导入会让她认错人，去重也会乱合并；
3. **密钥单独放**——数据和密钥躺在同一个目录，备份一起泄露等于没加密；
4. **改之前先备份**——`tools\backup-memory.ps1`，或手动拷 `memory\` 目录；
5. **别把「关于她自己」的设定写进记忆**——那是人设（`persona/core.md`），不是记忆。

## 七、给 AI 的部分（DeepSeek / DSH 会话请从这里读）

### 7.1 你的角色

你是「养护工」。你可以读、可以提议、可以在用户确认后写；**不能**在没确认的情况下批量删改。

按顺序做：**读 → 出计划 → 用户确认 → 分批执行 → 校验 → 记录**。

### 7.2 数据在哪

| 数据 | 路径 | 说明 |
|---|---|---|
| 记忆库 | `<dataDir>/memory/memory.json` | v2 密文信封；**只读，不要手改** |
| 人可读视图 | `<dataDir>/memory/memory.md.enc` | 密文；改了也没用 |
| 待核实区 | `<dataDir>/memory/pending.json` | 闸门拦下的条目 |
| 关系簿 | `<dataDir>/memory/relations.json` | 印象/亲密度，不是事实 |
| 池容量状态 | `<dataDir>/memory/memory-pool.json` | 记录是否已扩容 |
| 密钥 | `<dataDir 同级>/qq-whale-keys/memory.key` | 加密密钥，单独备份 |

`<dataDir>` 默认是 `~/.dsh/qq-whale`（DSH 插件配置里的 `dataDir` 可覆盖）。

### 7.3 接口契约（以插件宿主为准）

前缀：`/dsh-qq-whale`（宿主端口每次重启会变；控制台 `/api/overview` 的 `plugin.base` 是当前值）。

| 方法 | 路径 | 请求体 | 响应 |
|---|---|---|---|
| GET | `/memory/list` | — | `{ok, count, entries[]}`（按 `at` 倒序） |
| POST | `/memory/add` | `{kind, who, qq, text, weight}` | `{ok, entry, count, merged}` |
| POST | `/memory/update` | `{id, text?, kind?, who?, qq?, weight?}` | `{ok, entry}` |
| POST | `/memory/delete` | `{id}` | `{ok, deleted, count}` |
| GET | `/memory/pending` | — | 待核实列表 |
| POST | `/memory/pending/approve` | `{id}` | 先入库成功再出队 |
| POST | `/memory/pending/reject` | `{id}` | 只出队，不碰正式库 |

要点：

- `kind` 只能是七个正式值之一；`weight` 只能是 1~5；`qq` 必须是 5~12 位数字（空串合法 = 没有身份）；
- **`add` 的 `merged:true` 表示「内容相近，已经并进旧条目」**，返回的 `entry` 是旧的那条——别拿它的 id 去删；
- `delete` 对不存在的 id 返回 404，不会假报成功；
- 所有写操作都是**整份落盘**，所以一次别塞太多（分批，每次几十条）。

### 7.4 重新分类的标准作业流程（SOP）

**第 0 步：备份**

```
powershell -File <repo>\tools\backup-memory.ps1
```

确认 `D:\MollyBackup\memory\` 与 `${MOLLY_ROOT}Backup\memory\` 有最新一份。

**第 1 步：只读审计**

`GET /memory/list`，按 `kind` 统计条数，重点找：

- `kind` 明显错的（fact 里混着喜好、event 里混着长期事实）；
- 半截话（含「什」「这个字」「他希望」之类）；
- `qq` 为空却带名字的（旧数据，只能靠名字认人）；
- 同一人的重复条目（同 `qq`、文本相似）。

**第 2 步：出计划**（先别写）

产出一张表：`id → 现状 → 建议动作（改 kind / 改写 text / 删 / 补 address）→ 理由`。把「可删」和「需你看一眼」分开列。

**第 3 步：用户确认**

默认只执行「可删」与「改 kind」，涉及人称、隐私、`promise` 的一律等确认。

**第 4 步：分批执行**

- 改类：`POST /memory/update {id, kind}`；
- 补称谓：`POST /memory/add {kind:"address", who, qq, text:"叫他「X」", weight:5}`；
- 删除：`POST /memory/delete {id}`；
- 每批 ≤ 50，批间核对 `count` 变化。

**第 5 步：校验**

- `count` 应等于「原条数 − 删除数 + 新增数」；
- `address` 条数 = 活跃成员数（每人 1 条）；
- 提示词里 `# 怎么称呼` 段出现正确的名字；
- 控制台记忆页分布正常，待核实区没有新堆。

**第 6 步：记录**

在变更记录里写：删了多少、改了多少、补了多少、备份在哪。

### 7.5 `address` 专项规则（给 AI 的硬约束）

- 只从「叫他 X / 叫你 X / 喊他 X / 称呼「X」」解析；单字、疑问词、量词丢弃；
- 每人一条，`weight` 5；
- **没有明确来源就不要编**——宁可让她说「你」，也不要叫错；
- 提示词层面禁止泛称；你也不要往库里写「主人」「哥们儿」这类默认称呼。

### 7.6 什么绝对不能做

- ❌ 手改 `memory.json`（密文 + 整份覆盖，必坏）；
- ❌ 把 `pending.json` 里的条目直接拷进正式库（要走 approve）；
- ❌ 批量删除用户没确认的条目，尤其 `promise` / `address` / `person`；
- ❌ 跨人导记忆（`qq` 会错）；
- ❌ 一次塞几百条 add（会触发裁剪，还会互相合并）。
