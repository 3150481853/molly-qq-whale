# 记忆是怎么长出来的（memory-guide）

> 这个机器人**不是**靠"把聊天记录全存下来"记住事情的。
> 它是每聊几轮，让模型自己总结出几条「值得记的事实」，写进一个 JSON 文件。
>
> 理解了这一条，你就理解了它为什么记性好、也为什么记性差。

---

## 1. 一条记忆长什么样

记忆存在 `memory.json` 里，长这样：

```json
{
  "version": 1,
  "entries": [
    {
      "id": "mmexample0001",
      "kind": "fact",
      "who": "阿满",
      "qq": "123456789",
      "text": "他在广州，养了一只叫团子的猫。",
      "weight": 3,
      "at": 1792224107508
    }
  ]
}
```

七个字段，逐个说：

| 字段 | 类型 | 含义 | 注意 |
|---|---|---|---|
| `id` | string | 条目唯一 id，13 位小写字母数字 | CRUD 的更新/删除靠它。**别手改** |
| `kind` | string | 分类，见下表 | 决定召回时的意图匹配 |
| `who` | string | **名字**（群名片/昵称，可带 emoji） | 给人看的，会变 |
| `qq` | string | **QQ 号**，唯一身份 | 认人认这个。可能是空串 |
| `text` | string | 记忆正文 | 建议 < 200 字符，长了会被截断 |
| `weight` | number | 权重 1~5 | 越高越不容易被压缩掉 |
| `at` | number | 写入时间（毫秒时间戳） | **更新条目时不变** |

### 1.1 `who` 和 `qq` 为什么是两个字段

这是踩过坑的设计。

**名字是随时会改的**：群名片、昵称、备注，一天能改三次。
**QQ 号不会变**。

所以：

- `who` 只用于**显示**和"没 qq 时的退化匹配"；
- `qq` 才是**真正的身份**。

如果两条记忆 `who` 都是「阿满」但 `qq` 不同，那是**两个人**，不能混。反过来同一个人换了名字，靠 `qq` 能认出来。

**老条目可能没有 `qq`**（读时补空串，不写盘）。这类条目只能靠名字认人 —— 同名的人会串。

### 1.2 `kind` 的五个正式值

| kind | 什么时候用 | 例子 |
|---|---|---|
| `fact` | 客观事实 | 「他在广州。」 |
| `preference` | 喜好 | 「他喜欢历史人物游戏。」 |
| `promise` | 答应过的事 | 「他答应下周把书还我。」 |
| `person` | 对人的判断/印象 | 「他人挺实在，就是话少。」 |
| `event` | 发生过的事 | 「他生日那天在加班。」 |

另外还有两个**内部类型**，你不用手动写：

| kind | 来源 |
|---|---|
| `work` | 干活的执行日志（「我帮他做过：…」） |
| `sticker` | 表情包学习（模板写入，没有 who 也没有 qq） |

`work` 和 `sticker` 在质量闸门里被特殊对待 —— 比如 `work` 里出现"记忆"这个词是正常业务词，不该当垃圾拦掉；`sticker` 没有身份也不算「无主语」。

### 1.3 `weight` 怎么定

1~5，默认 3。

它是**保留优先级**，不是"重要性评分"：

- 库里条目超过上限（默认 400）时会按 `weight` 排序裁剪，`weight` 低的先掉；
- 召回打分里权重贡献很小（`weight * 0.3`），**不会**让高权重条目霸屏。

所以别把什么都写成 5。真正 5 的应该只有「这人是谁」这种。

## 2. 记忆是怎么被写进去的

### 2.1 三步流程

```
聊天进行中
    ↓
（每几轮）让模型看最近的对话，输出一批候选记忆
    ↓
① 质量闸门 judge()  ← 见第 3 节
    ↓ 通过
② 相似度去重 memory.add()
    ↓
落盘 memory.json + 重渲染 memory.md
```

### 2.2 闸门之后还有一道：相似度去重

`memory.add()` 自己会查一遍：

> 同一个人（同 `qq` 或同 `who`）+ 同 `kind` + 正文相似度 > **0.8**
> → **不新建**，而是把新内容**并进旧条目**（权重取两者较大值），然后**返回那条旧 entry**。

这意味着：**`add()` 返回的 entry 可能是旧的**，不一定是刚写进去的那条。

⚠️ **这是集成时最容易踩的坑**：如果你拿返回的 `id` 去执行删除，删掉的可能是用户真实存在的旧记忆。

判断方法：看返回的 `text` 是不是你刚写的那句。不是 → 说明发生了合并，**不要删**。

### 2.3 落盘是「整份覆写」

`memory.json` 的保存方式是**把内存里的整个数组写回文件**（先写临时文件再原子改名）。

所以：

- **不要直接改磁盘上的 `memory.json`** —— 插件下次 `add()` 会用内存里的旧数组把文件覆盖掉，你的修改静默消失；
- **要改就走控制台/接口**，让插件改内存再落盘。

同理 `memory.md` 是从 `memory.json` 渲染出来的**只读视图**，改它没用。

## 3. 质量闸门：什么会被拦下来

闸门是**表驱动**的，规则按顺序命中，先中先返回。

| 顺序 | reason | 拦什么 | 说明 |
|---|---|---|---|
| 1 | `no-identity` | `who` 和 `qq` 都空（`sticker` 除外） | 不知道记的是谁，没法用 |
| 2 | `insult` | 侮辱/占便宜的记录 | **排在 too-short 前面** —— 一句「傻逼」要报 insult 而不是"太短" |
| 3 | `too-short` | 去掉空白不到 4 个字 | |
| 4 | `self-talk` | 模型自言自语「这轮没什么可记的」 | 这类句子能到两百字，所以只查关键词 |
| 5 | `meta-narration` | 讲"我怎么记/系统提示"的元叙述 | 对 `work` 不生效（那是正常业务词） |
| 6 | `fragment` | 只是转述碎片（「他提到了 X 这个字」） | 去掉指代后剩不到 3 字 |
| 7 | `vacuous` | 无信息断言（不在意/无所谓/随便） | 12 字以内的空话 |
| 8 | `no-content` | 去掉标点表情后 < 4 实字，或纯数字 | |
| 9 | `duplicate` | 同一个人名下已有几乎相同的记忆 | 相似度 **0.9**，比合并层严格得多 |

### 3.1 规则崩了会怎样

**规则自己抛异常 → 一律放行。**

这是故意的：「宁可放过，不可错杀」。闸门写错不该导致记忆丢失。

### 3.2 被拦下来之后去哪了：待核实区

被拦的条目**不是直接删掉**，大多数会进「待核实区」（`pending.json`）。

```jsonc
{
  "id": "pmexample001",
  "kind": "fact",
  "who": "阿满",
  "qq": "123456789",
  "text": "他提到「祀」这个字。",
  "weight": 3,
  "at": 1792224107508,
  "reason": "fragment",
  "score": 0.83
}
```

分流规则：

| 情况 | 去向 |
|---|---|
| 通过 | 正式库，`added++` |
| `duplicate` | **直接丢**，`dup++`（重复的没必要审） |
| 其它 reject | 待核实区，`pending++` |

恒等式：**`rejected = pending + dup`**。控制台上四个数对不上就是有 bug。

待核实区的作用是**让人过一眼**：看着对的点"转正"，不对的点"丢掉"。它最多存 200 条，超了丢最旧的；同一个人 24 小时内说同一句话不会重复堆。

### 3.3 待核实区的边界（别为了"多拦一点"就越界）

该进待核实区的是：**关于她是谁 / 涉及她的侮辱或占便宜**（「他是你爹」「他说你是傻逼」）。

**不是**「所有提到脏字的记忆」：

- `work` 操作日志里转述的脏话 → 留在正式库；
- 表情包文件名里的脏字 → 留在正式库。

判据必须一直指向"她"，不能退化成关键词黑名单。

## 4. 记忆是怎么被想起来的（召回打分）

每次要说话之前，系统会从库里挑出**跟当前对话相关**的记忆塞进提示词。挑的过程就是打分。

### 4.1 打分公式

```
总分 = 身份分
     + 关键词分
     + weight * 0.3
     + 新鲜度 * 0.3
```

**身份分**（这三条互斥，取最高的）：

| 情况 | 分 |
|---|---|
| `qq` 命中当前说话人 | **+4** |
| `who` 同名 | **+2** |
| `who` 包含在名字里 | **+1** |

**关键词分**：把当前这句话切词，每个词命中记忆正文就加分：

```
词长 >= 3  → 基础分 3
词长 == 2  → 基础分 2
词长 == 1  → 基础分 1（只做加成，不算"真命中"）

实际加分 = 基础分 × max(0.15, idf(词))
```

`idf` 是"这个词有多罕见" —— 越罕见的词分越高。

**新鲜度**：`max(0, 2 - 天数/30) * 0.3`，也就是最近 60 天内有效，越新分越高，但**上限只有 0.3×2 = 0.6 分** —— 故意做得很小，避免"全是刚说的废话"把重要记忆挤掉。

### 4.2 过滤：宁可不说话，也不凑数

打完分之后有一层过滤：

```
没有任何关键词？
  → 全量参与排序（按身份 + 权重 + 新鲜度）

有关键词，且有"两字以上的词"命中？
  → 只留这些（相关性够硬）

只有单字命中，且原句 <= 2 个字？
  → 接受这些（比如问"猫"）

以上都不是？
  → 返回空数组 —— 宁可说"想不起来"，也不拿不相干的记忆凑数
```

### 4.3 兜底：泛问召回

「我喜欢什么」「我叫啥」「我生日是哪天」这类问句里**根本没有能命中记忆文本的词**。

比如记忆写的是「他养了一只猫叫团子」，问「我喜欢什么」时一个词都对不上 —— 上面直接返回空。可这正是最需要她记得住的时刻。

所以有一层兜底：**当关键词一分都没命中时**，认一下问句意图，直接回该人对应 `kind` 的高权重条目。

只在 `pool.length === 0` 时启用，不干扰正常检索。

### 4.4 召回窗口

| 场景 | 条数上限 | 单条字符上限 |
|---|---|---|
| 正常 | 24 条（本人）+ 8 条（相关） | 200 字符 |
| 降智档 | 8 条 + 4 条 | 200 字符 |

**降智档**是超出预算后切到弱模型时用的 —— 砍掉历史也砍掉记忆条数，避免"脑子不够用还念一大段"。

### 4.5 怎么调这个窗口

窗口参数在 `lib/memory.js` 顶部的 `MEMORY_WINDOW`：

```js
export const MEMORY_WINDOW = Object.freeze({
  contextLimit: 24,          // 本人记忆最多给几条
  queryLimit: 8,             // 相关记忆最多给几条
  degradedContextLimit: 8,   // 降智时本人
  degradedQueryLimit: 4,     // 降智时相关
  entryChars: 200,           // 单条截断长度
})
```

**要调只改这一处。** 别在业务代码里再写死数字 —— 写死了这里的调优就完全失效。

## 5. 记忆和关系是两回事

除了 `memory.json`，还有 `relations.json`。

| | 记忆 | 关系 |
|---|---|---|
| 内容 | 客观事实 | 主观印象/亲密度 |
| 例子 | 「他在广州」 | 「跟他聊天挺轻松」 |
| 谁写 | 模型总结聊天 | 关系系统按互动积累 |
| 怎么用 | 召回打分选几条 | 每轮都带（它是语气的底噪） |

关系是"你俩处到哪一步了"，会在每次回复时全部带进提示词（不筛选）。

## 6. 一条重要的原则：记忆从聊天里长出来

**不要把别人的记忆导入你的库。**

原因不是道德说教，是技术性的：

- `who` / `qq` 是这个人的身份锚点。导进来的旧记忆用的是**别人的** QQ 号和昵称，你的机器人会认错人；
- 相似度去重（0.8）是为"同一个人反复说同一件事"设计的。跨人导入会产生大量莫名其妙的合并 —— 新说的话被并进一条旧记忆，然后那条旧记忆的 id 被当成"刚写的"；
- `at`（时间戳）会被用于新鲜度打分。导进来的老记忆新鲜度是负贡献，会成为纯噪声。

**正确的初始化方式**：让库空着，正常聊天。几轮之后它自己会长出第一批。

如果你要预置一些**关于机器人自己**、不涉及具体人的设定（比如"她喜欢下雨天"），那种东西**属于人设（`core.md`），不属于记忆**。

## 7. 手工维护记忆

控制台提供完整的增删改：

| 操作 | 说明 |
|---|---|
| 列表 | 按 kind / who 过滤，看条数和分布 |
| 新增 | 填 `kind` / `who` / `qq` / `text` / `weight` |
| 更新 | 按 `id` 改字段。**`at` 不变** |
| 删除 | 按 `id`，需要二次确认 |
| 待核实区 | 逐条「转正」或「丢弃」 |

**为什么要走接口而不是改文件**：见 2.3 —— 直接改盘会被下次 `add()` 静默覆盖。

**手动加记忆的注意事项**：

- `text` 控制在 200 字符内，别写长段落；
- `kind` 用第 1.2 节那五个正式值，别自己造；
- **写完确认一下返回的 `text` 和你写的一样** —— 不一样说明它被合并进了别的条目；
- 批量导入请分批，一次几十条就够，多了会触发裁剪。

## 排错

### 1. 她明明应该记得，却说想不起来

按顺序查：

- **这条记忆真的在库里吗？** 去看列表。可能在待核实区，压根没进正式库；
- **`who` / `qq` 对不对？** 如果记忆存的是旧昵称、`qq` 又是空串，改过名之后就认不出来了；
- **问句是不是"泛问"？** 「我喜欢什么」这类靠兜底逻辑，兜底只认特定意图。换个问法试试：「我之前说过我喜欢什么吗」；
- **是不是降智档？** 降智时只给 8 + 4 条，可能被挤掉了。

### 2. 同一条记忆被记了好几遍

按顺序查：

- **`qq` 是不是空串？** 去重靠"同 `qq` 或同 `who`"，两个都空就永远判不出是同一人；
- **`text` 措辞差太多？** 相似度阈值是 **0.8**，超过就不合并。同一个事实换个说法（「他在广州」vs「他家在广州」）可能就低于阈值了；
- **`kind` 不一样？** 不同 kind 不合并。要么统一 kind，要么手工合并。

### 3. 记忆越来越多，回复越来越慢

- **看条数上限**：默认 400 条，超了按 `weight` + `at` 裁剪。如果一直涨不降，说明上限被调大了；
- **看 `text` 长度**：单条 200 字符，写长了会被截断但**没被清理**，仍然占排序开销；
- **看 `memory.md` 体积**：它是给人看的渲染视图，太大说明库里确实多。先按 `weight` 从小到大清一批低价值的；
- **别指望自动清理有效**：裁剪只在超过上限时触发，日常增长不会自动降。

### 4. 待核实区堆了一大堆没用的

先看 `reason` 分布：

- 全是 `fragment` → 模型在记「他提到了 X 这个字」这种碎片，属于模型总结质量差，换更强的模型会好；
- 全是 `vacuous` → 一堆「他不在意」「他无所谓」，同理；
- 全是 `duplicate` → 不会进待核实区（直接丢），所以你看到 `duplicate` 说明有 bug，恒等式 `rejected = pending + dup` 应该对不上；
- 有 `insult` → 这是设计上想让你看见的（「他是你爹」这类），别一键清空，逐条看。

### 5. 改了 `memory.json` 发现改动没了

**就是被内存里的旧数组覆盖了。**

插件启动时把 `memory.json` 读进内存，之后每次 `add()` / `update()` / `remove()` 都是**整份写回**。你直接改盘，中间插件又写了一次，你的改动就没了。

正确做法：**改文件前先停插件，或者干脆走控制台接口**。
