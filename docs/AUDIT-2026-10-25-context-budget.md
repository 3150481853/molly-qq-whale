**可直接落地的估算公式（零依赖）：**

```js
// 宁可按"中文偏多"估，宁可高估一点（token 预算超了会截断/收费，低估才危险）
const tokens ≈ Math.ceil(cjkChars / 1.55 + asciiChars / 4.6 + 40)
```

- 中文正文/规则类：取 **1.53~1.58**，建议 **1.55**（偏差 <±3%）。
- 英文单词/URL/代码：**4.6**。
- 纯 JSON/表格符号多的文本：**3.0**。
- 长句反复出现（如人设）实测 1.56，短散文略高（1.72），所以 1.55 是**偏安全**的取值。

## 4. 建议（按收益/风险排序）

| # | 建议 | 每轮省 | 风险 | 备注 |
|---|---|---:|---|---|
| A ✅ **已采纳 10-25** | 记忆窗口 `large(48/16)` → `balanced(32/12)` | **-934 token（-13.6%，已实测）** | 低 | 只改 `memory.js` 的 `WINDOW_PROFILE` 常量一行；48 条里后 16 条与本轮问题相关性最低。**已上线：6,869→5,935** |
| B | 历史 `contextLimit 60 → 40` | **~302 token（4.4%）** | 中低 | 60 条≈30 轮对话；降到 40 条≈20 轮，长对话里"刚聊到哪儿"还在，但要观察她是否开始忘上文 |
| C | 表情包目录只注入口语化标签（现在 195 张 → 454 字） | ~150 token（2.2%） | 低 | `catalogText({maxTags:60})` 已有上限；改成每轮只带 30 个高频标签即可 |
| D | system prompt 顺序「稳定段在前、变动段在后」 | 0（省钱） | 低 | 便于上游 **prompt cache 命中**：人设/规则等确定性内容放前，记忆/名册/活动放后。实测未开启缓存时无收益，但给未来留门 |
| E | 人设内核瘦身（1,876 字） | 200~400 token | 中 | 人设是性格来源，只能精修不能大砍；需主人拍板文风 |

**A 已上线（实测 -934 token/轮，-13.6%，一轮 6,869→5,935）**；B 若也采纳再省 ~302（合计 -18%）；C/D 为增量优化。都不需要装分词器。

不建议做的：

- **装 tokenizer**：官方分词器是 Python 依赖，装在 Node 插件里要额外进程/二进制；实测这 4 类文本用上面常数估就能到 ±5%，不值得为省 1 个依赖引入新的启动失败面。
- **把记忆换向量库**：739 条规模下，48 条窗口是刻意留的"性格记忆"，不是检索瓶颈；换库反而丢可控性。
- **激进压缩历史**：历史只占 13%，砍到 20 条省的 token 不如 A 一条建议，还会明显伤连贯性。

## 5. 结论

1. 审计时一轮回复 ≈ **6.9k token**，其中 **82.5% 是 system prompt**、13% 是历史。想省 token，主战场在「记忆段 + 人设/规则」，不在历史。
2. 零依赖校准可用：**tokens ≈ cjk/1.55 + ascii/4.6 + 40**，误差 ±5%，不需要引入分词器依赖。
3. 最小改动、最大收益：**A（记忆窗口降档）已上线，实测 -934 token/轮（-13.6%）**；B 待批（再省 ~302）。回退办法：`memory.js` 里 `WINDOW_PROFILE` 改回 `'large'`，不用动任何调用点。
