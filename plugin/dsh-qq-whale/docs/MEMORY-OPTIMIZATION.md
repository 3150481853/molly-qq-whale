# 记忆系统优化注意事项

这份文档只记**踩过的坑和验证过的做法**，不解释设计动机。每条都对应一次真实故障或一份实测数据，照做能少走弯路。

---

## 一、先度量，再优化

1. **自己造卷子，别照抄公开评测。** 公开评测判的是「模型答得对不对」，那需要人工 rubric；我们能确定性量的只有「召回」。所以卷子只测两层：
   - `可答`：上下文里凑齐了回答所需的词、且不含禁止词 → 对齐 rubric 语义；
   - `证据`：那条**原始锚条目**自己有没有被召回 → 衡量留存。

   两层分开的意义：一条记忆掉了，但库里另一条同义条目兜住了答案，这是「证据丢失」不是「答不出」。混在一起算会得出相反结论。

2. **day0 是送分题。** 若题目在「最近 N 轮窗口」里就有答案，那它考的是窗口和答题，不是记忆。造题时必须标注 `recent6_evidence`：至少一档要保证窗口内无答案。

3. **语料会自己长。** 线上库每天都在新增条目，两次跑分数字不同，先怀疑语料漂移，再怀疑代码。跑分必须锁快照（`--no-refresh` 或复制副本），并在报告里写清条数。

4. **没有量到的收益不进生产。** 改完先离线跑同一份卷子，逐格对比；没变好就默认关闭，留开关和迁移工具，而不是「反正不会更差」。

## 二、检索层

1. **只加向量、不加重排，收益极小。** 双塔余弦是两句各编码一次，语义近但互相看不见。缺的是交叉编码器重排。

2. **粗排 → 重排 → RRF 融合**，融合权重实测 0.8（重排）最好；纯重排会打乱粗排的可靠次序。zscore 归一化各档都更差。

3. **重排只能给「已进池」的条目排序。** 候选池生成阶段被词面闸门丢掉的条目，重排救不回来。真要救，得在候选阶段补：池子建好后按向量余弦再捞一批（本项目 `VECTOR_CANDIDATES`）。

4. **跨人条目要罚，但不能一刀切。** 未点名他人 → 词分 ×0.05 且取消「强命中」；正文里确实提到了目标人 → ×0.5；有效权重同步 ×0.5。

5. **无归属的「全群摘要」不许顶替本人。** 周信类条目谁的事都写，靠「真名」两个字就能排进前三。点名场景下权重砍到 0.35，且**不许进候选池**（只降分不够）。

6. **身份命中加过分，正文里再出现名字就不要再加。** 否则「A 说：[引用 @B：…]」这类转述靠说话人名字排前列，把真条目挤到几十名开外。

7. **预算按「截断后的长度」记账。** 上下文注入时会按每条上限截断，若按原始长度扣预算，一条千字流水账能吃掉四条配额。超长条目用 `continue` 跳过，别 `break` 掉后面的短条目。

## 三、写入层

1. **相对日期入库即归一。** 「明天」存成「明天（10月21日）」。口径：凌晨 0–5 点说的「明天」按**天亮后当天**算，不按日历加一天——照日历加会整体偏一天，看起来还对，比没有日期更糟。

2. **幂等要逐处判断，不要整句判断。** 整句「已经有日期就跳过」会让「今天（10月24日）……明天……」这种混合句后半永远补不上；而带不同单位（「这周」→「10月26日那一周」）的旧格式不匹配正则，每次装载都重写一遍，数据里出现「（10月19日那一周）」×5。

3. **「计划」不等于「已发生」。** 给条目打 `tense: plan | past`，计划类带 `dueAt`；过了截止 +12 小时仍未兑现 → 标 `unfulfilled` 并降权 0.5，**但正文不删**（「说过没做到」本身是信息）。
   - 别用裸「要/得/会」当计划征兆，会把「他要对我家猫做甚」也判成计划（实测 1660/4577）。
   - 降权就只降权：顺手把「强命中」也取消，会把条目直接挤出候选窗口，降权变删除。

4. **改口判定要三道闸。**
   - 任一字符串是引用/转述（`X 说：`、`[引用 @`）→ 不算改口；
   - 共享实词 ≥2 且占较小一侧 ≥0.34 → 才算同一件事；
   - 否定词必须**紧贴**关键词前 0–3 字，且只出现在一侧；再排掉固定搭配（「面无表情」「无语」「没毛病」…）。
   - 表情包（meme）直接不参与改口判定——两张不同的图，永远不是「同一件事的两种说法」。

5. **取代者不存在时不要再降权。** `supersededBy` 指向的条目已被删/未生成，旧条目仍按 0.4 惩罚，等于永久背锅。降权前先确认目标还活着。

6. **同题合并（可选，默认关）。** 同一件事被逐句抽成几十条时，靠调权重救不回来。判据：同身份 + 同类型 + 时间窗 + 实词包含度 ≥0.95 + 共享词 ≥5；命中则不新建，只刷新时间与权重，**不覆盖正文**（两句细节不同，谁替换谁丢细节）。

## 四、工程层

1. **同步调用链里别用 async fetch。** `recall()` 是同步的，中间没有 `await` 的位置；要打本地 HTTP 就用 `execFileSync('curl.exe', …)`，body 走临时文件（避免 Windows 命令行长度上限）。失败一律返回 `null`，完整退回关键词路，绝不抛。

2. **超时要给足。** 交叉编码器 40 条在 32 核 CPU 上热态 0.7–0.9s、冷启 5s。超时设 1.5s 会导致客户端提前断开（`WinError 10053`），表现是「每轮都白等 800ms 且没有结果」。给 4s / 8s，再靠缓存压平均延迟。

3. **一轮对话会召回两次**（组装上下文一次、引擎关键词召回一次）。向量按查询文本缓存、重排按「问题 + 头部 id」缓存，否则每轮延迟翻倍。

4. **两个进程写同一批分片 = 后写的覆盖先写的。** 改数据必须在插件停着的时候做；自检脚本（`check-prod`）本身会 load + save，别和正在跑的插件同时用。

5. **分词要小写。** 只认小写字母的正则会把 `What` 切成 `hat`、`Our` 切成 `ur`，英文全废。

6. **大文件下载必须流式。** 一次性 `arrayBuffer` 拉 90MB 在镜像源上会超时；`pipeline(Readable.fromWeb(r.body), createWriteStream())` 77 秒完成。

## 五、部署

1. 向量与重排需要本地模型：`bge-small-zh-v1.5`（约 92MB，512 维）+ `bge-reranker-base`（约 1.1GB）。放在一个目录，用 `--models` 指过去。
2. 服务端是 `tools/embed-server.py`（标准库 http.server + torch，无需新依赖）；插件启动时会尝试拉起它，起不来只 warn 并退回关键词。
3. 开关：`MOLLY_EMBED_OFF=1` 全关；`MOLLY_EMBED_URL` / `MOLLY_EMBED_PYTHON` / `MOLLY_EMBED_SCRIPT` / `MOLLY_EMBED_MODELS` 可覆盖；`MOLLY_TENSE=0` 关闭计划判定；`MOLLY_TOPIC_MERGE=1` 打开写入侧同题合并。
4. 成本：每轮净增约 1–1.7 秒（CPU）、常驻内存约 1GB 量级。**先在自己的语料上量收益，没提升就别开。**
